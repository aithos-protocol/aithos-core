## What changed, finding by finding

### BDER-001 — determinism anchored to an independent expected value

- The `[0xAB; 32]` Gherkin fixture is replaced by the B2 vector's
  `zone_dk_hex`, and the deep path is built from the vector's `folder_sids` /
  `section_sid`. The feature and the only corroborated expected values in the
  repository now share one fixture and one `include_str!` compile-time link.
- The `When` no longer clones a `NodePath`. The second derivation goes
  `path -> Display -> NodePath::parse -> node_key`, so "the same path" is
  rebuilt through the surface another implementation would use.
- Two `Then` lines were added to the contract: the key must equal
  `deep_section_key_hex` byte for byte, and the chain must be one labelled
  derivation per segment — with the literal `aithos-core/v1/d/<sid>` and
  `aithos-core/v1/s/<sid>` label forms pinned, and the derivation count
  asserted equal to the depth (domain invariant 10).

### BDER-002 — absence of relation instead of inequality

- `assert_ne!` on two `[u8; 32]` is replaced by two assertions: no label the
  production code can build bridges one sibling to the other, and neither
  sibling key yields the zone key back under any such label.
- The label alphabet enumerated is `folder_label`/`section_label` over sids
  0..9 plus `tag_label(tag)` — **including the held node's own label**, which
  is what an invertible step is exploited with.
- The 16-byte-window check (`b2_shares_window`) asserts that no contiguous run
  of the zone key survives into a child key. This is the assertion M4 fails.
- The first sibling key is additionally pinned to `folder1_key_hex`.

### BDER-003 — the universal negative bound to the key actually held

- The `Given` no longer has an empty body: it builds the two sibling spines
  from the vector, and both the `When` and the `Then` read them. No step
  reinvents its own sids.
- A positive control was added as its own `Then` line: the held key must equal
  `folder1_key_hex`. Substituting `[0x00; 32]`, `[0xFF; 32]` or an unrelated
  folder key now fails the scenario instead of leaving it green.
- The three hand-picked `assert_ne!` are replaced by an enumeration of every
  canonical path the production code can build from the held key: folder
  spines of length 0..=3 over sids 0..9, each terminated by nothing, by
  `s/<sid 0..9>` or by `t/<tag>`. **13 332 derivations**, and the size is
  asserted in the step so it can never drift silently. The Gherkin `Then`
  keeps its universal sentence; the step states the bound.
- The upward half of §02.5 — "never anything **above** or beside it" — is now
  asserted by a third `Then`: no production label walks the folder key back to
  the zone key, and none walks a section key back to its folder.

### BDER-004 — renaming something real

- The scenario no longer re-derives an unchanged path. It reuses the existing
  honest fixtures: `Given a published bundle with section "note1" in circle
  "projets/perso"`, `When the folder "perso" is renamed to "intime"` — which
  calls `Bundle::rename_folder` — and `And the edition is republished`.
- One new `Given` records the section key derived from the sids the bundle
  actually stores, before the rename. One new `Then` re-resolves the section
  **at its new display path**, asserts the sid is the same one, and asserts
  the derived key is byte-identical.
- The existing `Then the owner reads the same section at "projets/intime/note1"`
  closes the loop end to end.
- The now-unused `Given a zone key and a folder containing a section` and
  `When the folder is renamed` step definitions were deleted rather than left
  dangling.

### BDER-005 — widening "every descendant"

- Two further descendant shapes were added to the scenario that already killed
  five mutants out of five: a **grandchild** section under a sub-folder of the
  held folder, and a **tag anchor** at the held folder.
- Both keep what gives this scenario its power — the `Then` crosses
  `derive_key` from the held key against `node_key` from the zone key, two
  distinct computation routes, never a value compared to itself.
- The three descendant keys are asserted distinct.
- The step carries the audit's own precision: `node_key` is a pure function of
  a path with no notion of node existence, so "future descendant" is not a
  distinguishable case at this layer; the operational claim belongs to
  `e-mandates.feature`.

### BDER-009 — the `node_keys` accumulator

- `b2_pair()` asserts `node_keys.len() == 2` before any positional read, and
  the tag-view `Then` asserts `len() == 3` before its `BTreeSet` cardinality
  check. Composing this feature's `Given`s can no longer shift the compared
  pair silently.

Two readings this report will not smooth over:

1. **M3 survives the sibling scenario.** A monolithic hash still produces
   unrelated siblings and is still one-way, so that scenario has no reason to
   see it. M3 is caught by scenarios 1 and 3, and the per-segment assertion of
   BDER-001 is the assertion that exists to catch it.
2. **The rename scenario kills no `node_key` mutant, by construction.** It
   compares a before/after pair inside one run, so a mutated `node_key` moves
   both sides together. That is the correct shape: the plausible regression
   BDER-004 names is not "names leak into `node_key`" — it is
   `Bundle::rename_folder` implemented as delete-and-recreate, which R1
   reproduces and which the scenario now catches. Before this correction R1
   left the scenario green.

The definition of done in the public audit is met on both counts: each of M1
to M5 fails at least one `b-derivation` scenario, and M5 fails four, above the
required three.

## Limits of this conclusion

- Six mutants are six points in an infinite space. "5 / 5" is evidence of
  discriminating power, not a calibrated mutation score.
- The 13 332-path enumeration bounds only the label space the production code
  itself can build from a held key. The universal negative of BDER-003 rests
  on BLAKE3 one-wayness and is not testable in principle.
- Scenario 6 and the `wrap` anchoring semantics of §02.9 are unchanged and
  remain `PARTIAL` pending the BDER-006 decision.
- BDER-007 and BDER-008 remain open: the tag-anchor invariant still has no
  independent witness, and the B2 vector's provenance claim is still not
  reproducible from this repository.
- This role does not mark anything `VERIFIED`.
