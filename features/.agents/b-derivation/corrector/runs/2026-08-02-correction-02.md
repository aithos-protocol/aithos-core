### 2. The correction of `BDER-008` mechanically forces a third file

`vectors/ownership.json` pins the SHA-256 of every vector, and
`aithos_bundle::vectors_ownership::vectors_match_their_pinned_digests` asserts
it over the **whole file bytes**, `description` included. Rewriting the
description therefore breaks that test unless the digest is re-pinned in the
same change — which `vectors/README.md` already requires ("Adding a vector means
adding its manifest entry … in the same change").

The decision arbitrated on 2026-08-02 authorises exactly this: the frozen-vector
rule protects the **values**, and no value changes. The manifest edit is a
mechanical consequence, not a second correction:

```text

                        ->  ec5be7976b62a9d2810ccfcdc598d9b6bbdcbdaee0b1960db384a875a01abe75
```

The manifest's own `updated` field is dated accordingly. No other entry, owner,
digest or rule in `ownership.json` is touched. The reviewer should confirm that
re-pinning a digest after a `description`-only rewrite is the intended reading
of README rule 3; the alternative reading — that rule 3 freezes the file bytes
and not the values — would make the arbitrated decision unexecutable, and that
contradiction is not a corrector's to resolve.

## What changed, finding by finding

### BDER-006 — the `Rule` title no longer promises §02.9

Before:

```gherkin
  Rule: Tag views anchor at folders
```

After:

```gherkin
  Rule: Each tag anchor is a distinct derivation
```

Why this wording. The retracted title is the headline of `spec/02-content-tree.md`
§2.9, which promises four behaviours: the anchor grants nothing by derivation
downward, sections enter it by `wrap`, a folder-local view spans that subtree
only, a zone-root view spans the zone. The Rule contains one scenario, whose
`Then` asserts that the tag-view anchors derived at a folder and at the zone root
differ from each other and from the folder key. That is a derivation property and
nothing else: one `derive_key` step under the `aithos-core/v1/t/<tag>` label
(`derive.rs:38` `tag_label`, applied at `derive.rs:54`), distinct per holding
node. The new title
states exactly that and promises no anchoring semantics. The `wrap` half of §2.9
lives in `aithos-bundle` and is owed by the `d-bundle` cycle, per the decision.

No behavioural change: no scenario, step, tag or comment was modified. The
Cucumber block still reports 3 rules / 6 scenarios / 30 steps, identical to the
round-1 candidate.

### BDER-008 — the provenance claim states what is actually true

The retracted sentence was `Expected values generated independently (Python
blake3).` The replacement states, in the `description` itself:

- no independent B2 generator exists in this repository;
- the vector, its Gherkin fixtures and
  `rust/crates/aithos-core/tests/b2_derivation.rs` were all created in the same
  commit `1b7d258`;
- `folder1_key_hex` is recomputed from `zone_dk_hex` by five Python scripts —
  `gen-f.py:104-109`, `gen-g.py:150-153`, `gen-h.py:67-73`, `gen-h2.py:94-100`,
  `gen-i.py:75-81`;
- `deep_section_key_hex` is recomputed by `gen-f.py:107-109` alone;
- `sibling_section_sid`, `sibling_section_key_hex`, `tag` and both
  `tag_anchor_*_hex` fields have no external witness and are self-certified by
  `aithos-core::derive` through `b2_derivation.rs`;
- the values are unchanged and stay frozen;
- an independent `gen-b2-derivation.py`, to be named there per README rule 1,
  remains the only way to give the tag-anchor invariant an external witness.

Provenance facts were re-established directly, not copied from the audit:


The five/one corroboration counts were re-read in the scripts themselves, not

what is observed here.

Two wordings coexist in the inputs for the uncorroborated set: the decision
