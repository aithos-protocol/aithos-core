### A non-recipient opens nothing

- Steps:
  - `Given a sealed header for the owner and a grantee` → `cucumber.rs:7552-7565`, `Header::build(DID_C, NODE_A, &DK, &[owner_rec(), grantee_rec("g1",0x21)], &[eph(1),eph(2)], &[non(1),non(2)])` → `w.header`. Two lines: `lines[0].kid = "owner-kex"`, `lines[1].kid = "g1"`.
  - `When a third keypair tries every line` → `cucumber.rs:8096-8101`: `for kid in ["owner-kex", "g1"] { w.open_into(1, kid, 0x99); }`.
  - `Then it recovers nothing` → `cucumber.rs:12334-12338`.
- Parameter flow: `open_into` (`cucumber.rs:7396-7404`) calls `self.header.as_ref().unwrap().open(DID_C, version, kid, &xsk(sk_byte))`, maps the error to `String`, and **pushes the `Result` onto `w.opened`**. The "third keypair" is `xsk(0x99) = StaticSecret::from([0x99;32])` — distinct from the owner `0x0A` and the grantee `0x21`. Two entries are recorded. Each `Header::open` reaches `open_line` exactly once (one line matches each kid), where `X25519(0x99, epk)` produces a shared secret different from the one used at seal time, hence a different KEK, hence AEAD tag failure (`seal.rs:121-129`); `Header::open` then falls through to `Err(SealRejected("no line opens for kid {kid} on /e/circle v1"))` (`header.rs:242-245`).
- Assertion: `assert!(!w.opened.is_empty())` and `assert!(w.opened.iter().all(Result::is_err))`. This compares nothing to the header's contents. Answering the assigned question precisely: **the third keypair attacks both lines, two attempts are recorded, and the assertion proves only that every *recorded* attempt failed — not that every *line* was tried.** Coverage of the whole line set is a property of the hardcoded literal `["owner-kex","g1"]` in the `When`, never of any assertion. Two concrete ways the scenario stays green while proving less than it says: (a) if the fixture gained a third line with a new kid, the loop would skip it and the `Then` would still pass; (b) if a kid literal stopped matching any line, `Header::open` would return `Err` at `header.rs:242` **without performing a single decryption**, and the scenario would pass vacuously. Nothing asserts `w.opened.len() == header.key_versions["1"].lines.len()`.
- Spec comparison: §3.1 (`spec/03-headers.md:31-33`) — `to`/`kid` are routing hints, the seal is what grants. The adversarial model in the step (a stranger impersonating both kids) is the right one and is faithful to `DOMAIN.md` invariant 4. The current behavior is correct; the gap is in the strength of the proof, not in production code.
- Provisional verdict: `PARTIAL` (finding CHDR-RU1-c). Under the code as it stands, coverage happens to be complete, so this is a proof-strength defect, not a live behavioral defect.

### A corrupted line fails closed

- Steps:
  - `Given a sealed header for the owner and a grantee` → same `cucumber.rs:7552-7565`.
  - `When one byte of a line's ciphertext is corrupted` → `cucumber.rs:8103-8111`.
  - `Then opening that line is rejected` → `cucumber.rs:12340-12344` (`fn opening_rejected`, shared with the next scenario via the alias at `:12341`).
- Parameter flow / what is corrupted: `let c = &mut kv.lines[0].c; let flipped = if c.starts_with('0') { "1" } else { "0" }; c.replace_range(0..1, flipped);`. `lines[0]` is the owner line (recipients are zipped in order at `header.rs:91`; `owner_rec()` is first at `cucumber.rs:7559`). `c` is the hex ciphertext, 96 chars (32-byte DK + 16-byte Poly1305 tag). The mutation rewrites the **first hex character**, i.e. the high nibble of ciphertext byte 0. It always changes the value (`'0'→'1'`, otherwise `→'0'`, and the "otherwise" branch is only reached when the char is not `'0'`). It keeps the string valid hex and the same length, so `hex::decode` at `header.rs:236` still succeeds and the failure genuinely occurs inside the AEAD (`seal.rs:121-129`), not on the encoding-rejection path. **Answering the assigned question: yes, the corruption is applied to a ciphertext byte (its high nibble) and it does reach the AEAD.** The step then calls `w.open_into(1, "owner-kex", 0x0A)` — the *true* owner key against the *corrupted* owner line, which is the right shape for the claim.
- Assertion: `assert!(w.opened.last().unwrap().is_err())`. It compares the last recorded `Result` against `Err`, nothing else. **It does not distinguish a rejection caused by corruption from any other rejection.** `Header::open` returns the identical `Error::SealRejected("no line opens for kid owner-kex on /e/circle v1")` (`header.rs:242-245`, rendered by `error.rs:35-36` as `seal rejected: …`) for a wrong key, a wrong AAD (`did`/`node`/`version`), a corrupted byte, and even for "no line carries that kid at all" — the last of which involves zero cryptography. The scenario also has **no positive control**: it never asserts that the same line opened before the mutation, so a fixture regression that made the owner line unopenable for an unrelated reason would leave the scenario green.
- Partial effects: the mutation is performed by the test on `w.header` in memory; no production build/rejection path is exercised, so there is no partial-effect surface here to prove. The World is per-scenario (`runner/basic.rs:1439`), so the corrupted header cannot leak into another scenario. Nothing asserts that `epk`, `n`, `to`, `kid` or the sibling `g1` line were left intact, so the assertion also does not exclude an over-broad mutation as the cause.
- Spec comparison: §3.8 (`spec/03-headers.md:120-127`) and the doc comment at `seal.rs:108-109` state the fail-closed property for "wrong key, wrong AAD (node/version/did), corrupted byte" — the three causes are deliberately indistinguishable at the API. That makes it the *test's* responsibility, not the API's, to attribute the rejection; here it does not. `c1_header_seal.rs:92-94` is the only place that isolates the corrupted-byte cause (`c[5] ^= 1` around a known-good baseline), and it does so at the `open_line` level, not through `Header`.
- Provisional verdict: `PARTIAL` (finding CHDR-RU1-b). The corruption itself is well-formed and does reach the AEAD; the assertion is what is too weak to attribute the rejection.

## Candidate findings

**CHDR-RU1-a — the "version" half of `A line is bound to its node and version` is never exercised**
- Severity: medium.
- Impact: the scenario title and the Rule assert binding to node **and** key version, but only the `node` AAD component is varied. A regression that dropped `key_version` (or `subject_did`) from `line_aad` would leave all four RU-1 scenarios green. Cross-version line replay — the exact protocol threat behind §3.8 — has no Gherkin coverage.
- Evidence: `features/c-headers.feature:26-29`; `rust/crates/aithos-bundle/tests/cucumber.rs:8113-8122` (both `Header::build` calls are version 1 via `rust/crates/aithos-core/src/header.rs:116`; `open_into(1, …)` at `cucumber.rs:8120`); AAD assembled at `rust/crates/aithos-core/src/seal.rs:21-31`, `:35-37`. The only version-mismatch check in the repository is `rust/crates/aithos-core/tests/c1_header_seal.rs:105-107`, at the `line_aad`/`open_line` level, not through `Header`, and not reached by any scenario.
- Expected behavior per spec: `spec/03-headers.md:124-126` binds `subject_did ‖ node ‖ key_version`; `DOMAIN.md` invariant 3 requires replay across any of the three to fail closed.
- Smallest correction: in `replay_line_other_node`, after the existing node-replay attempt, add a second attempt that transplants the same v1 owner line into a v2 `KeyVersion` of the *same* node (or opens it with `version = 2`) and record it in `w.opened`; then have the `Then` require both recorded attempts to be `Err`. Alternatively split the scenario into two so the Gherkin no longer claims more than one variation.

**CHDR-RU1-b — rejection assertions do not prove the stated cause and have no positive control**
- Severity: medium.
- Impact: `opening_rejected` accepts any `Err`. `Header::open` emits the same `Error::SealRejected("no line opens for kid …")` for a wrong key, a wrong `subject_did`/`node`/`key_version`, a corrupted byte, and for the no-matching-kid case in which no decryption is attempted at all. Scenarios 3 and 4 therefore prove "opening returned an error", not "opening was rejected *because of the corruption*" / "*because of the node rebinding*". Neither scenario establishes that the same line opened before the mutation, so an unrelated fixture breakage that made the owner line permanently unopenable would keep both green.
- Evidence: assertion at `rust/crates/aithos-bundle/tests/cucumber.rs:12340-12344`; single undifferentiated error at `rust/crates/aithos-core/src/header.rs:242-245`, rendered by `rust/crates/aithos-core/src/error.rs:35-36`; the deliberate indistinguishability is documented at `rust/crates/aithos-core/src/seal.rs:108-109`. Mutation sites: `cucumber.rs:8103-8111` and `:8113-8122`.
- Expected behavior: per `DOMAIN.md` ("A rejection assertion must prove the rejection is the one the scenario claims") and `docs/audits/features/README.md:55-68`.
- Smallest correction: make each rejection scenario differential inside itself. In `corrupt_line`, call `open_into` once **before** flipping the nibble and once after, and have the `Then` assert `opened[0] == Ok(DK)` and `opened[1].is_err()`; additionally assert that `epk`, `n`, `to`, `kid` and the sibling line are unchanged, so the only varied input is the ciphertext. In `replay_line_other_node`, record a control open of the stolen line on its original header before the transplant. This attributes the rejection without needing a new error variant.

**CHDR-RU1-c — `tries every line` is a hardcoded kid list, and `it recovers nothing` never ties the attempts to the header's lines**
- Severity: low-to-medium.
- Impact: the `When` iterates the literal `["owner-kex", "g1"]` rather than `header.key_versions["1"].lines`, and the `Then` requires only "non-empty and all `Err`". A line added to the fixture would be silently untried; a kid literal that stopped matching any line would produce a vacuous `Err` from `header.rs:242` with zero decryption performed, and the scenario would still pass. Under the current code coverage is in fact complete, so this is a proof-strength defect, not a live behavioral defect.
- Evidence: `rust/crates/aithos-bundle/tests/cucumber.rs:8096-8101` (hardcoded list), `:12334-12338` (assertion), `:7396-7404` (`open_into`), `rust/crates/aithos-core/src/header.rs:233` (kid filter) and `:242-245` (vacuous `Err` path).
- Expected behavior: `spec/03-headers.md:31-33` / `DOMAIN.md` invariant 4 — a reader tries every line matching its kid and the AEAD decides; the scenario claims the stranger tries *every* line.
- Smallest correction: derive the kid list from the header (`w.header.key_versions["1"].lines.iter().map(|l| l.kid.clone())`), and strengthen the `Then` to `assert_eq!(w.opened.len(), lines.len())` in addition to `all(is_err)`.

**CHDR-RU1-d — no RU-1 scenario reaches the C1 vector, and the `Header` layer's wire bytes are never vector-anchored**
- Severity: low.
- Impact: `Owner and grantee each open their line` proves self-consistency between a seal and its own open. The byte-exact conformance proof (`vectors/c1-header-seal.json`) is exercised only by `c1_header_seal.rs`, which calls `seal_line`/`open_line`/`line_aad` directly and never constructs a `Header`. Consequently nothing cross-checks that `Header::build`'s assembled line (`epk`/`n`/`c` hex fields, AAD built from `self.node` and the decimal version) reproduces the vector bytes. A change confined to `header.rs` — e.g. mis-ordering the recipient/ephemeral zip at `header.rs:91`, or passing a different `node` string into `line_aad` — would not be caught by the vector.
- Evidence: fixture constants `cucumber.rs:259-284` vs vector values in `vectors/c1-header-seal.json` (`subject_did`, `dk_hex`, `esk_hex`, `n_hex` all differ; only `node = "/e/circle"` coincides); `rust/crates/aithos-core/tests/c1_header_seal.rs:55-81` never touches `Header`.
- Expected behavior: `DOMAIN.md` — "Strengthen byte-exact cryptographic cases with `vectors/c1-header-seal.json` rather than with self-consistency between a seal and its own open"; `docs/audits/features/README.md:65-66`.
- Smallest correction: add one assertion in `c1_header_seal.rs` that builds `Header::build(v.subject_did, v.node, dk, [owner, grantee], [esk…], [n…])` from the vector inputs and compares `key_versions["1"].lines[i].{epk,n,c}` with `epk_hex`/`n_hex`/`c_hex`. This is a core-test addition, not a Gherkin change, and leaves the scenario's behavioral role intact.

**CHDR-RU1-e — the `Given` of `Owner and grantee each open their line` stores nothing**

- Impact: `dk_and_two_recipients` has an empty body and an unused World parameter; the stated precondition ("a node key and two recipients") is not established by the `Given` but by the `When`, and its "parameters" are compile-time constants, not scenario inputs. Removing the `Given` would not change any outcome. Additionally, the `When` reuses the `Given` step function of scenarios 2 and 3 (`cucumber.rs:8093` → `:7552`), so a single helper defines both a precondition elsewhere and the act under test here.
